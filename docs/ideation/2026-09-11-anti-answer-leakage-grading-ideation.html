Ideation: Anti-Answer-Leakage Grading

Prevent lazy empty submissions from receiving a full rubric checklist that doubles as an answer key. Grade and display only what the student actually submitted; use generic failure messages for missing or wrong components.

Grounding Context

Codebase context. The OOP AutoGrader scores correctly against a PostgreSQL rubric via reflection (Class), MMD parse/compare, and operational testcases. The leak is in the display assembly layer, not scoring.

ClassStructureService builds student-facing Class and MMD tabs by iterating the full rubric checklist. When ParsedSubmissionSnapshot has no entry for a member (empty file, missing class, or wiped ephemeral snapshot), assembly falls back to rubric labels:

  • snapshotAttributeName(..., rubricFallback) returns rubric field/method signatures when snapshot key absent.
  • Class tab else branches (~lines 569–632) emit rubric name, scope, dataType, returnType, and param lists.
  • MMD relations without snapshot use rubric from/to/relType.

StudentUI.jsx renders backend strings verbatim in monospace — no client redaction. Hidden operational testcases already omit I/O (TestcaseResultMapper); Class/MMD have no equivalent.

Past learnings. Parsed snapshots live in ephemeral SUBMISSION_BASE_DIR/_parsed_snapshot/; missing files trigger rubric fallback (documented in backend AGENTS.md). No prior solution doc for answer leakage.

External context. CodeGrade, Gradescope, and HackerRank use tiered visibility (hide config/output/result). Gradescope recommends custom failure messages instead of assert diffs that leak expected strings. Research (Ji et al.) suggests gap feedback on visible checks while keeping hidden checks opaque.

Topic Axes

  • Backend display assembly — ClassStructureService, LabResultAssembler, DTO shaping
  • Snapshot & submission presence — what was parsed vs rubric iteration
  • Student UI feedback presentation — generic copy, partial credit visuals, accessibility
  • Role-based / time-gated disclosure — lecturer full view vs student opaque view
  • Testcase pillar parity — extend hidden/redacted pattern to structure pillars

Ranked Ideas

1. DisclosureMode Student Assembler

Axis: Backend display assembly Confidence 92% Complexity Medium
Description
Collapse buildClassData, buildClassDataFromRubric, and MMD builders into one assembler parameterized by DisclosureMode.STUDENT | LECTURER. In STUDENT mode, null snapshot entries never receive rubric-shaped strings — only generic placeholders and pass/fail flags. Upload lab_result and GET /class//mmd both use STUDENT mode for student JWTs.
Basis
direct: Identical rubric-fallback logic in upload assemble and revisit GET paths (ClassStructureService.java lines 569–632 and 694–749).
Rationale
One policy flip at the server stops leakage before StudentUI can render it. Scoring via ClassReflectionGrader / MmdComparisonService stays unchanged.
Downsides
Requires threading role/mode through controller → service; must audit all student read endpoints (upload bundle, GET tabs, history).

2. Submitted-Only Row Manifest

Axis: Snapshot & submission presence Confidence 88% Complexity Medium
Description
Build Class/MMD tabs from ParsedSubmissionSnapshot keys only — classes and members the student actually declared. Unmatched rubric criteria roll up to aggregate counts (e.g., “4 of 9 required members not found”) without naming them. Zero-submission challenges show pillar empty states with scores only — no rubric-derived cards.
Basis
direct: ParsedSubmissionSnapshotBuilder stores matched artifacts only; ClassStructureService still iterates full rubric for every row.
Rationale
Matches the user’s “grade only what was submitted” requirement literally. Empty uploads no longer feel like a graded walkthrough of the answer key.
Downsides
Students lose per-missing-member row granularity unless paired with rollup copy; score pill math must stay consistent with hidden rubric rows.

3. Hidden-Member Parity (Testcase Pattern for Structure)

Axis: Testcase pillar parity Confidence 90% Complexity Low
Description
Generalize TestcaseResultMapper’s hidden-row behavior: for each rubric member without a snapshot entry, emit a locked summary row (pass/fail icon, no name/type/signature) or omit the row entirely while preserving aggregate score pills. Snapshot-matched members keep expandable detail with student-sourced labels only.
Basis
direct: Hidden testcases omit input/expected/actual display strings; Class/MMD expose full rubric member rows today.
Rationale
Fastest path to cross-pillar consistency — reuses a tested redaction model instead of inventing a second disclosure system.
Downsides
May feel opaque if rollup copy is too terse; lecturers need a separate full checklist (see Idea 4).

4. Dual-Audience DTO Split

Axis: Role-based / time-gated disclosure Confidence 85% Complexity Medium
Description
Student endpoints return opaque ChallengeDetailBundleDTO (or a fork) with redacted member fields. Lecturer challenge drawer and plagiarism views keep today’s full rubric checklist via existing ?studentId= reads with DisclosureMode.LECTURER. Optional mirror endpoint GET .../rubric-checklist for teaching review.
Basis
reasoned: One DTO currently serves student dashboard and lecturer inspection; tightening student view must not regress lecturer workflows.
Rationale
Separates teaching/review surfaces from student feedback surfaces so anti-leak fixes never strip lecturer tooling.
Downsides
Two shapes to maintain; Swagger and frontend lecturer paths need explicit mode tests.

5. Tri-State Feedback UI + Copy Taxonomy

Axis: Student UI feedback presentation Confidence 87% Complexity Medium
Description
Frontend message layer (ui-ux-pro-max aligned) mapping backend status to a fixed taxonomy:
  • Not submitted — text-foreground-disabled, lock icon, “Required member not found in your submission”
  • Wrong attribute — show student’s parsed label + generic hint: “Missing or wrong variable or data” (scope/type/modifier category without expected value)
  • Partial — existing orange warning-bg + minus tick; triple-encoded (color + icon + text) for WCAG
Basis
direct: StudentUI.jsx renders {f.name}: {f.dataType} verbatim; statusClasses.js and semantic tokens already exist in tokens.js.
Rationale
Backend redaction is necessary but not sufficient — copy and affordances must teach that something failed without teaching what to write. Use role="alert" for parse errors per UX guidelines.
Downsides
Frontend-only layer is bypassable via raw API; must pair with Ideas 1–3. Requires new DTO fields like feedbackCode or submitted: boolean.

6. Anti-Leak CI Regression Suite

Axis: Backend display assembly Confidence 82% Complexity Low
Description
JUnit fixture: given a graded submission with correctIds populated but snapshot forcibly null, serialize student-role Class/MMD DTOs and assert no rubric-shaped strings (method signatures, param types, relation endpoints from rubric). Denylist regex fails the build on regression.
Basis
direct: TestcaseResultMapperTest covers hidden testcase redaction; no equivalent leakage test for Class/MMD snapshot absence.
Rationale
Compounds the fix into a durable contract — future display tweaks cannot reintroduce rubric fallbacks unnoticed.
Downsides
Does not fix leakage by itself; must follow Ideas 1–3.

7. Durable Snapshot Persistence (JSONB)

Axis: Snapshot & submission presence Confidence 78% Complexity High
Description
Persist ParsedSubmissionSnapshot to Postgres (submission_display_snapshot JSONB) at grade time instead of ephemeral _parsed_snapshot/ files. Read paths never reconstruct display from rubric after Render storage wipes.
Basis
direct: Backend AGENTS.md documents missing snapshots cause rubric fallback on class type labels; worst-case full answer key on legacy reads.
Rationale
One migration removes an entire class of leakage incidents and improves history-tab consistency — compounds grade-time capture into durable state.
Downsides
Operator SQL migration; storage size; still needs DisclosureMode for members never captured in snapshot.
