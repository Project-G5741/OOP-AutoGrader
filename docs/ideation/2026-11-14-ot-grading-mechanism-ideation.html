Ideation: OT grading mechanism improvements

Date: 2026-11-14 Topic: ot-grading-mechanism Focus: OT upload wall-clock / throughput mechanisms Mode: repo-grounded
Grounding Axes Ranked ideas Rejection summary

Grounding Context

Codebase context. After class+MMD, upload/bulk OT runs as one lab-wide OP_BATCH behind host workerJvmSlot (Semaphore(1)). Local warm reuse exists (SharedLocalWorkerCache) but default worker-idle-ttl-ms=0 closes on release. In-worker pool is min(items, CPUs, ot-batch-parallelism); host transport wait is items×timeout+30s. Class --reflect, OT, and dry-run share the same unfair slot. Desktop keeps the same TestcaseGrader/worker.jar path, forces sandbox off, and caps OT pool at 2.

Past learnings. Rejected: student invoke in API JVM; per-testcase remote RTT; nested grading-executor joins; inventing a second student OT runner. Kept: batch IPC + execution-only timeout; hang → halt → respawn remaining; desktop/web/bulk scoring-logic parity.

External context. Online judges prefer warm-then-destroy sandboxes and process-as-kill-boundary. PrairieLearn zygote is the Python warm pattern; HotSpot cannot fork safely. Reflection-based OT (live student heap) is a published gap — batch IPC buys warmth and couples timeout, contamination, crash, and slot occupancy.

Note: codebase-scan subagent was blocked once; grounding used in-thread AGENTS/docs + four evidence dossiers. Verifier ran fresh-context.

Ranked Ideas

1. Reflect vs OT slot 2. Parallel transport lease 3. Dirty-bit warm park 4. Priority admission 5. Chunked OP_BATCH 6. Heap/Metaspace pool governor 7. Shootdown→SCRAM ladder

1. Detach --reflect from the OT host slot (or fold it into one OT lease)

Host slot fairness Confidence 88% Complexity Medium

Class-tab --reflect already acquires workerJvmSlot during class+MMD (untimed), then OT acquires again and often cold-opens a second JVM. Either give reflect its own short lane, or hold one lease that runs reflect IPC then OP_BATCH on the same session — so declaration parsing stops stealing OT’s only host worker.

basis direct: ReflectionClassParser acquires the same unfair Semaphore(1) as OT/dry-run; OT only borrows SharedLocalWorkerCache after class+MMD. Verifier: sound.

rationale. Slot=1 was meant to bound OT isolation; today it also serializes Metaspace-safe parse and can inflate worker_slot_wait_ms for students while lecturer dry-runs barge.

downsides. A second reflect process raises concurrent RSS briefly; a unified lease lengthens hold time if reflect is slow. Must keep student types out of the API JVM.

2. Parallelism-aware transport lease (stop paying serial for a parallel batch)

Lab-wide batch IPC & in-worker parallelism Confidence 90% Complexity Low

Host wait is itemCount × timeout + 30s even though the worker already runs up to P items concurrently. Size the lease as ⌈T/P⌉ × timeout + slack (optionally shrink as items complete via heartbeats) so one Midterm lab does not monopolize workerJvmSlot for a serial-pessimistic ceiling.

basis direct: WorkerSessionHandle.transportWaitSeconds ignores pool size; WorkerInvokeEngine.resolveBatchPoolSize already parallelizes. Verifier: sound.

rationale. Upload pain is often slot occupancy for other waiters, not just student-code CPU.

downsides. Under-budgeted waits risk false outer timeouts if the pool stalls; need careful slack and hang detection.

3. Dirty-bit / demand-gated warm park (use the cache you already shipped)

Worker lifecycle / warm reuse Confidence 92% Complexity Low

Default TTL 0 always closes after OT/dry-run, so every upload pays cold ProcessBuilder spawn. Keep RSS-safe defaults, but park when the slot has queued waiters (or after clean batches), and destroy only when hang dirt marks the session — “warm pool, destroy dirty,” not “always bank the furnace.”

basis direct: SharedLocalWorkerCache already parks for positive TTL and never caches sandbox; tests cover reuse. External: warm-then-destroy sandboxes. Verifier: sound.

rationale. Highest leverage-per-LOC: the mechanism exists; the policy defaults it off on the bottleneck path.

downsides. Parked RSS on small hosts; must never park sandbox/remote sessions; dirty-bit bugs could reuse a contaminated JVM.

4. Priority / fair admission on workerJvmSlot

Host slot fairness Confidence 85% Complexity Medium

Replace unfair Semaphore(1) with a fair (or priority) admission queue: STUDENT_UPLOAD / BULK > DRY_RUN > REFLECT, fair within band. Capacity stays 1 — fairness is queueing, not multi-tenant concurrency. Time waits for every path, including reflect.

basis direct: TestcaseInvokeExecutorConfig builds unfair new Semaphore(1); three contenders documented. External: boarding groups / PriorityClass under a single gate. Verifier: sound.

rationale. Capacity-1 is intentional; barging makes student latency a lottery under lecturer dry-run bursts.

downsides. Lecturer UX can feel “stuck” behind uploads; needs clear metrics and maybe aging so dry-run is not starved forever.

5. Challenge-chunked OP_BATCH under one borrowed session

Lab-wide batch IPC & in-worker parallelism Confidence 80% Complexity Medium

Keep one session and one TestcaseGrader, but send per-challenge (or fixed-size) batches instead of one lab-wide megabatch. Smaller transport leases, smaller hang blast radius, less 4MiB line pressure — without returning to per-testcase RTT.

basis direct: gradeLab flattens all runnable OT into one invoke; handle already slices/respawns after hang. Learning: batch not per-testcase RTT. Verifier: sound.

rationale. Lab-wide batch won RTT; it also couples wait formula and hang radius to whole-lab size.

downsides. More IPC round-trips; must preserve identical scoring/order semantics; careful with composition state that is per-item today.

6. Metaspace / heap governor for OT pool size (one math, many envelopes)

Desktop / offline parity Confidence 78% Complexity Medium

Desktop hard-codes ot-batch-parallelism=2 against Midterm parallel URLClassLoader OOMs while giving a fat heap; cloud uses CPU count. Replace profile folklore with one resolveBatchPoolSize that takes free heap/Metaspace + item count — same jars, different resource envelopes, same scores.

basis direct: desktop YAML cap vs cloud 0=CPU; each concurrent item owns a loader. Project rule: grading logic must match; resource caps may differ. Verifier marked literal “unify to 2” weak — this survivor is the Metaspace-unit reframing, not forcing cloud to 2.

rationale. Turns “desktop is slow by leftover OOM fear” into a measurable sizing policy that keeps parity honest.

downsides. Estimation wrong → OOM or under-parallelism; needs golden Midterm soak tests on both profiles.

7. Soft shootdown, then SCRAM (hang isolation ladder)

Isolation & kill boundary Confidence 62% Complexity High

Today first TIMED_OUT cancels siblings and Runtime.halt(0)s the worker. Keep SCRAM as the hard trip for interrupt-immune loops, but first try ClassLoader/thread-local shootdown (or process-per-suspect for the toxic item) so healthy siblings finish without a full respawn tax.

basis direct: cancel-rest + halt on TIMED_OUT; worker AGENTS note interrupt-immune loops. External: process-per-test kill boundary; TLB-shootdown analogy. Verifier: weak vs current poison contract — kept as ambitious isolation direction, not a quick win.

rationale. One hung Midterm item currently taxes the whole lab’s remaining work via respawn under slot=1.

downsides. Soft isolation is hard to prove safe; false “clean” reuse is a security/reliability footgun; high design cost.
