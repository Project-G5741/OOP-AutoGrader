Fresh ideation (not a continuation of the same-day overloading doc). Overriding means inheritance polymorphism: same signature, subclass body runs when invoked through a parent/interface type. That is orthogonal to overloading (same name, different params).

Grounding context

Codebase context

  • Operational testcase types are UNIT | COMPOSITION only. CONCEPTS states polymorphism / inheritance / encapsulation are not OT types this ship.
  • Runtime polymorphic dispatch already exists in the worker: when dispatchClassName is set on a method step, WorkerInvokeEngine resolves via getMethod on the dispatch type and invokes on the named receiver. Covered by ae1GetAreaThroughShapeUsesCircleOverride (Circle area through Shape → 12.5).
  • Without dispatch, lookup is getDeclaredMethod on the concrete class — no virtual call through a supertype.
  • Frontend always forces dispatchClassId: null in empty/normalize/member-pick paths. No lecturer control in Unit or Composition worksheets.
  • Declaration Test matches methods by name + parameter types on the declaring class; heritage is Extends/Implements shell only. No getDeclaringClass override evidence; no @Override grading.
  • oop_principle_tag was wiped by the OT migrator; enum/DTO leftovers remain but are not the product model.
  • Student Operation Test pillar is still dark (testcaseApplicable = false); lecturer dry-run is the live loop.

Past learnings

  • No docs/solutions/ entry on method overriding. Closest: operational grading stack, receiver-constructor pitfalls (Unit hidden receiver unfit for polymorphic call sites), Composition multi-step order_index, sync-by-presence saves.

External context

  • Prior art (ASys/JavAssess, Miami AutoGrader, Kelas): reflection hierarchy + behavioral invoke — rarely a first-class “override” lecturer primitive.
  • Canonical structural idiom: subclass method’s getDeclaringClass() ≠ superclass. @Override is SOURCE retention — absent from bytecode.
  • Traps: overload ≠ override; static same-signature = hiding; bridge/synthetic for covariant returns.

Core difficulty (one sentence)

The engine can already prove override behavior; authoring erases the switch, Declaration Test cannot prove behavior, and a new TestcaseType would fight CONCEPTS — so the hard problem is product posture + UX, not inventing a third grader.

Ranked ideas

1. Call-as dispatch 2. Differential proof 3. Behavior-first posture 4. Override Lab dry-run 5. Declaring-class diagnosis 6. Eligibility + traps
#1 Behavioral + Authoring + Product Conf 90% Cx Medium

Call-as: uncap dispatchClassId on Composition (not a third type)

Stop nulling dispatchClassId in testcaseAuthoring.js. On Composition method steps, add a Call as: <supertype> control populated from the receiver’s Extends/Implements ancestors. Persist the existing DB column; worker path already proven by AE1. Keep TestcaseType as UNIT | COMPOSITION — override is a step capability, not a passport type.

Basis
direct: WorkerInvokeEngine dispatch branch + ae1GetAreaThroughShapeUsesCircleOverride; testcaseAuthoring.js always sets dispatchClassId: null; CONCEPTS forbids polymorphism as an OT type; invocation DTO already carries dispatchClassId.
Why it matters
Highest leverage/cost: “implement an override testcase” mostly means stop erasing a live capability and give lecturers a Call-as control — without a migrator wipe or a third type.
Downsides
Lecturers must understand billed-role vs actor (Call as Shape ≠ rename Circle). Multi-supertype graphs need a picker, not a silent default. Unit should stay out of scope (hidden receiver unfit).
#2 Semantic traps Conf 85% Cx Medium

Differential override proof (dual-path / paired expecteds)

A single happy return through parent dispatch is not enough — empty overrides, hardcoding, and instanceof switches still fool positive-only checks. Require differential evidence: invoke through the parent with subclass-expected behavior, and optionally pair with a concrete-path or parent-default contrast so pass-through fails. Encode this as a Composition macro or twin assertions, not a new grader opcode.

Basis
direct: 2026-09-17 plan R13/AE2 — Declaration can mark override present while empty overrides pass; worker forks getDeclaredMethod vs getMethod. external: Liskov-style contract tests / prodrug “activation” assays — dose via declared route, measure active metabolite.
Why it matters
Answers the pedagogical difficulty: what fails when students “have” the method but do not specialize behavior.
Downsides
Authoring cost rises; auto-generated traps can be noisy if parent default is undefined. Prefer lecturer-owned expecteds over smell detectors.
#3 Product + Structural Conf 88% Cx Low–Medium

Behavior-first posture: OT proves override; Class only diagnoses

Do not score “override exists” as a separate OT type or as a Class all-or-nothing row that greenlights empty methods. Primary grade = polymorphic invoke + assertions. Structural declaring-class evidence (idea #5) is a failure-diagnosis sidecar and authoring filter — not a substitute for AE1-shaped behavior.

Basis
direct: CONCEPTS separates Declaration Test from OT; plan language already splits “signature present” from “override works.” Verifier concurred this is the correct product posture.
Why it matters
Prevents shipping a false-green Class tab and calling the override problem solved.
Downsides
Lecturers who only use Class tab still lack a polymorphism signal until OT authoring ships. Messaging must be explicit in guides.
#4 Product sequencing Conf 82% Cx Low

Lecturer Override Lab via dry-run while student OT stays dark

Treat student-pillar darkness as a feature window, not a blocker. Ship Call-as + differential scripts for lecturers; validate against reference Java with existing dry-run (TestcaseGrader.gradeSingle). Light student OT later as a separate policy decision — do not gate it on “has a dispatch step.”

Basis
direct: testcaseApplicable = false globally; dry-run already runs the worker. Rejected sibling: gating student OT on dispatch presence (blocks non-inheritance labs).
Why it matters
Unblocks validating override pedagogy without student-facing risk or a premature pillar light-up.
Downsides
Lecturers invest in OT that students cannot see yet — set expectations in docs.
#5 Structural Conf 70% Cx Medium

Declaring-class capture for diagnosis and filters (not primary score)

Extend reflection parsing to record Method.getDeclaringClass() (bridges/synthetics already skipped). Use it to (a) explain dry-run failures (“signature present but declared on parent only”), and (b) constrain Call-as options / eligibility. Do not treat declaring-class alone as override proof — empty bodies still declare on the subclass.

Basis
direct: repo has zero getDeclaringClass usage; Class matcher is name+params only. external: industry structural idiom — useful but incomplete without behavior.
Why it matters
Closes the structural half of the dual-evidence gap without pretending Class tab can grade specialization.
Downsides
Verifier marked “weak” as primary proof — keep scope diagnostic. Covariant returns / bridges need care.
#6 Semantic traps Conf 78% Cx Medium

Override-eligibility predicate + trap taxonomy

Central isOverrideEligible(parent, child): same name+params, non-static, parent not final, declaring classes differ, bridges skipped. Surface three exclusive lecturer intents for same-name methods — overload / override / hide — so authoring cannot collapse them. Never trust @Override as runtime evidence (SOURCE retention).

Basis
direct: overload already disambiguated by method-id labels; no hiding vocabulary in grading docs; UI nulls dispatch so traps never surface. external: Oracle override vs hide; SpotBugs-style hiding checkers; @Override SOURCE-only.
Why it matters
Makes the classroom difficulties first-class so Call-as does not become “another signature picker.”
Downsides
Auto-companion trap suites can over-generate; start with validation messages + optional packs.

Difficulty map (what makes this hard)

  • Capability vs surface gap: worker + DB column exist; every authoring path nulls them — Composition can look polymorphic while using concrete getDeclaredMethod.
  • Structural ≠ behavioral: name+params (and even declaring-class) greenlight empty overrides; only parent-typed invoke + differing expecteds prove specialization.
  • Unit canvas mismatch: one member + hidden receiver cannot express “subclass instance, parent call site.”
  • Vocabulary collision: overload UX is rich; override UX is absent; static hiding and bridges are undocumented traps; @Override is unreliable at runtime.
  • Product-model trap: a third TestcaseType (or revived principle tag) contradicts CONCEPTS and the OT migrator — step capability is the appropriate shape.
  • Student pillar timing: student OT is dark; lecturer dry-run can still validate override labs first.

Appropriate approach (compressed)

Prefer #1 + #2 + #3 + #4: Composition Call-as (uncap dispatch), differential assertions, behavior-first scoring, lecturer dry-run first. Add #5/#6 as diagnostics and trap vocabulary — not as a new OT type and not as @Override scraping.
