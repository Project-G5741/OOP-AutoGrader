Grounding context

Today the student experience is a Vite React SPA (StudentDashboard.jsx) that talks to Spring Boot on VITE_API_URL. Upload grading is server-side: compile per challenge, load rubric from LabRubricCache (PostgreSQL), reflection + MMD + operational testcases via GradingService and an isolated backend-1.0.0-worker.jar JVM. History and lab lists come from /api/submissions/* and GET /api/labs. Auth is Google OAuth or IRN/password → JWT with session version checked against the database on each request.

An offline executable must reproduce enough of that pipeline locally while respecting term enrollment, lab visibility, deadlines, and attempt numbering that today live only on the server.

Critical blockers

Beyond remote rubric storage, these gaps block a faithful “same product, no network” clone unless explicitly designed around.

Grading engine footprint — Upload requires a JDK (JavaCompilerService), parallel compile workers, and often a separate worker JVM for operational testcases. A desktop bundle must ship or detect Java 17+ and the worker JAR, not just a static UI.
Master data + OT graphs — Rubrics reference master_data (scope, relation types, etc.) and deep operational testcase invocation trees. A rubric export must include these or local grades diverge from the server.
Policy gates on upload — StudentTermAccessService.requireUploadAccess enforces current term, enrollment, active account, lab in current quarter, student_visible, and release_date. Offline logic needs a frozen policy snapshot or students could submit when the web app would 403.
Deadline and “official” score semantics — Server scoring for records uses qualifying submissions before lab deadline (Vietnam end-of-day). Offline attempts after deadline or with stale deadline data would not match lecturer grade overview.
Attempt identity and sync — Attempt numbers are MAX+1 in a single JDBC transaction on the server. Offline grading creates local attempts that must merge without collisions when the machine reconnects.
Result detail assembly — Class/MMD/testcase tabs combine rubric, element results, compile-error sidecars, parsed snapshots under SUBMISSION_BASE_DIR, and student disclosure rules. Missing snapshot files already force fallbacks on the server; offline must generate equivalent local artifacts.
Authentication without Google — Google sign-in is unusable offline. IRN/password still expects a live /api/auth/login and JWT whose sv claim is validated against PostgreSQL unless you add device-bound offline credentials (new security model).
History source of truth — my-history and my-labs are aggregate SQL over all quarters. Pure offline history is only what was synced or created locally unless you embed a database replica.
Plagiarism and peer comparison — Post-upload plagiarism compares git metadata and file hashes to other students in the same lab. That cannot run meaningfully offline without a peer corpus; skipping it changes lecturer-facing integrity signals.
Rubric mutability — Lecturers edit structure and testcases; cache TTL is 30 minutes in production. A stale local rubric produces scores the server would reject or recalculate differently after sync.
Packaging size and platforms — Shipping Spring Boot + PostgreSQL/SQLite + JDK guidance for Windows (primary student OS) is hundreds of MB and needs code signing, updates, and AV false positives.
Security of exported rubrics — Student disclosure hides some lecturer fields, but local rubric bundles still increase leakage risk if the executable is reverse-engineered (expected answers in OT assertions).

Topic axes

  • Local grading parity (compile, reflection, MMD, worker OT)
  • Policy and rubric snapshots (term, labs, deadlines, visibility)
  • Identity and session without cloud auth
  • Persistence, history, and upload sync
  • Desktop shell and distribution

Ranked ideas

  1. Signed term pack + slim local grading CLI
  2. Hybrid offline grade, online sync queue
  3. Embedded local API (mini Spring + SQLite)
  4. Tauri/Electron shell over existing SPA + localhost backend
  5. Pre-login online “bootstrap” only
  6. Offline history viewer + online submit split

1. Signed term pack + slim local grading CLI

Description
Lecturer or ops publishes a signed term pack (rubrics, master data, lab policy, optional OT graphs) per current quarter. Desktop app imports pack, runs extracted grading kernel + worker JAR against student uploads, stores attempts in SQLite. Sync uploads when online.
Axis
Policy and rubric snapshots
Basis
direct: LabRubricCache and requireUploadAccess today assume live PostgreSQL; pack replaces DB reads for grading session.
Rationale
Separates “what to grade against” from “where grades are recorded,” directly addressing the rubric blocker without cloning the full cloud database.
Downsides
New export/signing pipeline; pack refresh when lecturers edit labs; must keep pack format in lockstep with schema migrators.
Confidence
72%
Complexity
High

2. Hybrid offline grade, online sync queue

Description
Same UI as web wrapped in desktop; grading runs locally using last-synced rubric; submissions sit in an outbox (zip + metadata) until connectivity returns, then POST to existing /api/submissions/.../upload. Server remains authoritative for attempt numbers and plagiarism.
Axis
Persistence, history, and upload sync
Basis
direct: Upload pipeline already persists atomically on server; queue preserves API contract.
Rationale
Smallest change to lecturer/analytics surfaces; students see immediate local feedback while official record catches up online.
Downsides
Duplicate work if local and server grades differ after rubric change; queue conflicts need UX.
Confidence
78%
Complexity
Medium

3. Embedded local API (mini Spring + SQLite)

Description
Ship app.jar + worker + embedded SQLite seeded from sync; React build points VITE_API_URL to 127.0.0.1. Reuse controllers/services with a “local mode” profile.
Axis
Local grading parity
Basis
direct: Backend AGENTS.md documents full pipeline in one JVM + worker; highest behavioral fidelity.
Rationale
Minimizes reimplementation of MMD/OT/disclosure edge cases already handled in Java.
Downsides
Largest download; two PostgreSQL dialect assumptions to abstract; startup time and RAM on low-end laptops.
Confidence
65%
Complexity
High

4. Tauri/Electron shell over existing SPA + localhost backend

Description
Package current frontend dist with a launcher that starts bundled backend process and opens a webview. Password change UI omitted per product rule.
Axis
Desktop shell and distribution
Basis
reasoned: Fastest path to “executable” if backend+DB problem is solved separately (ideas 1–3).
Rationale
Reuses almost all React student flows documented in frontend/src/pages/AGENTS.md.
Downsides
Does not by itself solve rubric or auth offline; still two processes to manage.
Confidence
85% as packaging layer only
Complexity
Low–Medium

5. Pre-login online “bootstrap” only

Description
Require one online session per week (or per lab release) to refresh JWT, term pack, and history delta; all submit/grade sessions afterward are offline until pack expires.
Axis
Identity and session without cloud auth
Basis
direct: JWT sv session validity and Google OAuth assume periodic server contact (jwt-session-version-force-logout learning).
Rationale
Relaxes pure-offline auth while keeping most study time disconnected.
Downsides
Violates strict “no internet” if bootstrap window is missed; needs clear expiry UX.
Confidence
70%
Complexity
Medium

6. Offline history viewer + online submit split

Description
Export read-only history JSON/SQLite for offline browsing; keep submit on web only.
Axis
Persistence, history, and upload sync
Basis
reasoned: Reduces scope when full offline grade is deferred.
Rationale
Unblocks history in dormitories with poor connectivity without local rubric.
Downsides
Does not meet stated goal of offline submit + live results.
Confidence
90% technically, 20% product fit
Complexity
Low
